# Update

Codifix v3.1.0 is the current stable release. Start with the version currently running on the **service** you intend to upgrade. A machine can have several named instances with independently pinned binaries.

## Upgrade Codifix 3.0.0 to 3.1.0

1. Record the selected instance, running binary version, database identity and configuration. Choose one existing project and a known record you can read again after the upgrade.
2. Schedule a maintenance window. Stop writers sharing that database, preserve the instance configuration, credentials and release files, and take a recoverable PostgreSQL backup. Rehearse the upgrade against a restored copy.
3. Choose the matching [platform package](/docs/install) and verify its checksum against the [3.1.0 release](https://github.com/3vilM33pl3/codifix/releases/tag/v3.1.0). Stage the binary and matching web assets for that instance. Named instances keep their own executable pins.
4. Keep the existing database and instance configuration. Version 3.1.0 adds migrations after `0085` through `0105`. Apply them once through the instance's configured migration procedure. For a `verify_only` runtime, use the authorized migration owner first, confirm the runtime can access the new tables and sequences, and retain the existing runtime privileges.
5. Start the selected service. Check readiness and database health, confirm the running service version, then open the chosen project and read back the known record in **Memories**. For a client configured for this instance, the following commands also check the connection and project identity:

```bash
codifix --version
codifix health
codifix status --project example-app
```

Replace `example-app` with the project you recorded. The first command identifies the local CLI. Check the service version in the health output or the instance's health endpoint. Resume writers after the checks pass. If the upgrade fails after new writes, preserve that work and use a reviewed forward repair or restore the matched backup with its prior binaries and configuration.

## Before a v2-to-v3 cutover

For Memory Layer v2.x, follow the [Codifix 3 reinstall procedure](https://github.com/3vilM33pl3/codifix/blob/v3.1.0/packaging/CODIFIX-3-REINSTALL.md). This change introduces new executable, package and service identities. Keep matched copies of the original database, configuration, credentials, attachments and state for reconciliation.

## v3.1.0 package names

Use the [Install package table](/docs/install) for filenames. On macOS, use the application-update package to preserve an existing Codifix runtime. The [Linux Desktop client](/docs/desktop) has its own version. The [release compatibility guide](/docs/help/known-limitations) covers platform and signing details.

## After an approved installation

Follow the [service checks](/docs/help/doctor-and-health) and verify your normal project workflow. If this service hosts Network and Inbox, also check the [companion upgrade procedure](https://github.com/3vilM33pl3/codifix/blob/v3.1.0/docs/user/network-inbox-upgrade.md).
