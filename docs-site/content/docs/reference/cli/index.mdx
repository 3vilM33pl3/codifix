# CLI reference

The `codifix` CLI is the primary automation surface for Codifix. It configures projects, runs the backend, captures work, curates memory, answers questions, manages embeddings, opens the TUI, exposes MCP, and runs evaluations.

Use command help as the final source of truth before scripting:

```bash
codifix --help
codifix <command> --help
codifix <command> <subcommand> --help
```

## Global options

| Option | Env var | Purpose |
|---|---|---|
| `--config <path>` | `CODIFIX_CONFIG` | Use a specific global config file. |
| `--area <name>` | `CODIFIX_AREA` | Select an operator-configured knowledge area. |
| `--area-routing <path>` | `CODIFIX_AREA_ROUTING` | Use an operator-owned area routing policy, outside repositories. |
| `--writer-id <id>` | `CODIFIX_WRITER_ID` | Override the advisory writer label for captures and activity; authenticated principal identity is authoritative. |
| `--agent-id <id>` | `CODIFIX_WRITER_ID` | Alias for `--writer-id`; it changes the label, not authorization. |

Many commands also support `--project <slug>`, `--json`, or `--dry-run`. Prefer `--json` for agent automation and `--dry-run` before commands that write config, memory, history, embeddings, or repo metadata.

## Command shape

Most commands follow one of three shapes:

| Shape | Example | Notes |
| --- | --- | --- |
| Root command with flags | `codifix query --project memory --question "..."` | Common for query, scan, remember, status, doctor. |
| Command group with subcommand | `codifix commits sync --project memory` | Common for service, watcher, repo, graph, bundle, eval, embeddings, checkpoint. |
| Foreground long-running command | `codifix service run` | Runs until interrupted; use service managers for packaged background operation. |

## Agent contract

Agents should follow a repeatable command pattern:

1. Run `codifix query` before answering project-specific questions.
2. Run `codifix resume` after interruptions or context loss.
3. Use `codifix checkpoint start-execution` when beginning approved plans.
4. Use `codifix remember` after meaningful completed work.
5. Use `codifix status`, `codifix doctor`, and `codifix health` before blaming retrieval or the TUI.

## Read/write guide

| Kind | Mostly read-only | Writes local or service state |
|---|---|---|
| Setup | `completion`, most `dev` inspection | `wizard`, `init`, `upgrade`, some `dev` scaffolding |
| Service | `status`, `doctor`, `health` | `service enable`, `service disable`, `service restart-all`, `watcher flush` |
| Query | `query`, `resume`, `up-to-speed`, `activities`, `history`, `verify-provenance` | Query/activity logging may write audit events when the service is running. |
| Memory | `proposals list`, `scan --dry-run` | `remember`, `capture`, `curate`, `scan`, proposal approval/rejection, `archive`, `prune-history` |
| Reinforcement | `scores`, `review list` | `validate`, `review apply`, `review reject` |
| Evidence | `repo status`, `graph status`, `embeddings list` | commit sync, repo indexing, graph extraction, embedding reindex/reembed/prune, bundle import |
| Integrations | `mcp status`, watcher status, `loops list`, eval compare | watcher start/stop, loop settings/runs/approvals, MCP HTTP service config, eval run artifacts |

## Project resolution

Area routing first chooses the installation; the project slug scopes knowledge
inside it. A project name is not a cross-area identity. Inspect the area and
instance in status before writing. See [Areas and projects](/docs/areas) and
[routing precedence](/docs/how-it-works/area-routing).

Commands that operate on memory need a project slug. In normal repo-local use, the CLI can read `.codifix/project.toml`; in automation, pass `--project <slug>` explicitly so the command does not depend on the current working directory.

```bash
codifix query --project memory --question "What changed in the docs site?"
codifix status --project memory --json
```

## Output contracts

Commands intended for automation prefer JSON output where supported. Usage mistakes, such as missing required flags, normally exit with code `2`. Operational failures normally exit non-zero and include a human-readable error on stderr.

Use `codifix status --project <slug> --json` as the first broad diagnostic when command behavior looks wrong.
