# Operations

Codifix is local-first, but it still has operational concerns: service health, database availability, backups, logs, privacy, and upgrade safety. Use this page as a runbook, not a second copy of the troubleshooting guide.

## Baseline

```bash
codifix health                          # backend service
codifix doctor                          # config and dependencies
codifix status --project <project-slug> # combined service, watcher, MCP, doctor
```

Run these once at the start of an incident or change. After that, move to the relevant section below instead of repeating them.

## Service

The service runs as a systemd unit on Linux or a launchd agent on macOS. Use standard OS tools to start, stop, and inspect it. See [Service setup](/docs/install/service-setup) for initial configuration.

| Task | Command |
|---|---|
| Run in foreground for debugging | `codifix service run` |
| Enable packaged background service | `codifix service enable` |
| Inspect configured service | `codifix service status` |
| Restart known service components | `codifix service restart-all` |
| Regenerate or confirm API token | `codifix service ensure-api-token` |

The foreground run command is intentionally blocking. If it exits, the service is not running from that terminal.

## Database

PostgreSQL with pgvector is the authority for durable memories, provenance and service ledgers. Configuration, credentials, local logs, caches, exports and release artifacts also live outside the database. See [PostgreSQL and pgvector](/docs/install/postgresql-pgvector) for setup.

## Backups and restore

### What to back up

- PostgreSQL database.
- Global configuration.
- Repo-local `.codifix/` project config.
- `.agents/` integration files if they are part of the project workflow.

### Basic database backup

```bash
pg_dump "$DATABASE_URL" > codifix-backup.sql
psql "$DATABASE_URL" < codifix-backup.sql
```

For production-grade backups, prefer custom-format dumps, checksums, restore tests, and a retention policy. Verify a restore by running `codifix doctor` against a disposable database.

Do not commit secrets, API keys, local database URLs, or runtime state.

## Upgrades

The current source workspace declares `3.0.0`; consult the release inventory for the exact source commit and package bytes. Follow the
[Update guide](/docs/install/update) and selected release evidence for package
installation, migrations and rollback. Historical v1-to-v2 changes are migration
context, not the current release designation.

Named areas/instances can pin independent releases. Installing a package or
running `service restart-all` does not upgrade those pinned releases. Use the
reviewed selected-instance upgrade procedure for the platform and exact target.

Before upgrading, take a baseline and back up the database:

```bash
pg_dump "$DATABASE_URL" > codifix-before-upgrade.sql
```

After the selected installation's upgrade procedure has completed, verify it:

```bash
codifix doctor
codifix health
codifix status --project <project-slug>
codifix upgrade --dry-run
```

Run `codifix upgrade` inside repositories only after reviewing the dry run, because it can refresh `.agents/` and other repo-local integration files.

## Areas and background work

An operator-configured area selects a service/data boundary; projects scope
knowledge within it. A durable job records work, attempts and effects; queued,
running and completed are different states. Federation exchanges approved
publications or explicitly authorized private expertise across instances; it does
not make global project search an unrestricted remote query. Supervisor policies
govern opt-in bounded agent work and accounting separately from jobs and ordinary
memory queries. Source implementation does not establish deployment readiness.

Use [Areas and projects](/docs/areas) to verify the destination,
[Jobs](/docs/reference/cli/jobs) for enrichment failures,
[Offline](/docs/offline) for pending contribution receipts, and
[Federation](/docs/federation) for publication and expertise recovery.

## Logs and diagnostics

| Surface | Use it for |
|---|---|
| `codifix doctor` | Configuration, database, provider, and environment checks. |
| `codifix status --project <slug>` | Combined project, service, watcher, MCP, and health view. |
| `codifix loops runs --project <slug>` | Automation run ledger and recent loop outcomes. |
| TUI Errors tab | Persisted diagnostics with fix hints and raw errors. |
| Web UI Errors tab | Same diagnostic model in a browser surface. |
| OS service logs | Startup failures, migrations, port conflicts, crashes. |

Redact provider tokens, database URLs, prompts, and local file paths before sharing logs publicly.

## Security and privacy

Codifix can be local-first, but external embedding or LLM providers may receive text depending on your configuration.

### Check before enabling integrations

- Which database stores project memory?
- Which LLM provider is configured?
- Which embedding provider is active?
- Is MCP HTTP local and token-protected?
- What does the watcher capture?
- Are logs redacted before sharing?

<Warning>
Do not expose the service or MCP HTTP route directly to the public internet.
For remote multi-user access, enable Authentik mode, terminate HTTPS at a
trusted reverse proxy, keep service-token clients scoped, and add network
controls. HTTP MCP remains cookie-blind and needs its own service token.
</Warning>

## Multi-project use

One backend serves multiple projects. Each project has its own slug, config, watchers, and scoped queries. Use `codifix status --project <slug>` to inspect each one independently.

## Web UI

The [Web UI](/docs/web-ui) is served by the same local service. Use it when you need a wider inspection surface for memories, query evidence, activities, review proposals, errors, embeddings, and resume briefings.

Keep the service bound to local interfaces unless you have explicitly
configured [Authentication and access](/docs/reference/authentication), HTTPS,
trusted proxy behavior, and network controls.

## Automations

The [Automations](/docs/automations) control plane is service-owned. Treat it like an operational surface: inspect settings before enabling loops, prefer dry-runs when exploring outputs, and review approval requests before accepting memory or repository changes.
